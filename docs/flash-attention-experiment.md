## 保留的问题

1. 固定 batch、head 数和 head dimension，观察序列长度增长时，显式计算 Attention 与官方 FA2 的延迟和峰值显存增量。OOM 如实记录，不将分析估算当作实测峰值。
2. 改变 batch × heads、序列长度和 head dimension，观察普通前向的并行行为；记录实际 kernel 与是否分派到 split-KV，不由 API 名称推断执行路径。
3. 对比普通与 causal attention，分析可跳过的 tile 和边界 masking 对实际执行的影响。
4. 视需要加入 PyTorch SDPA，但必须明确实际 backend；历史 FA1 仅在依赖兼容、来源可固定时作为独立对照，不将性能差直接归因于单一改动。

不再安排手写 Triton kernel 或自定义 kernel 消融。只读源码能够证明运算与任务结构，不能代替每项改动的实测贡献。

## 恢复实验前补齐

- 硬件获取已确认；补齐执行环境与并发，固定官方版本、镜像或既有环境与依赖。
- 定义完整测试矩阵、正确性阈值、输入分布和边界案例、输出文件及完成条件。
- 准备代码与镜像，将同一硬件上的设备确认、正确性、性能、显存和必要 profiler 检查合并到一次申请与一次远端调用。
- 执行前查询当前费率，分别估算准备/构建、排队、GPU 占用和结果回传时间，以及 GPU、CPU、内存和适用存储费用；明确预算与占用上限。
- 配置对应的超时、容器上限、重试限制和异常结果保存；结束后核查资源释放。未知时间与费用保留为未知，不填零。
