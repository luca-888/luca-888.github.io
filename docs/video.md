# 文章视频

这里记的是做视频时的思路，不是必须照做的格式。不写具体的尺寸、颜色、时间或题材例子；每部视频按主题单独设计，哪条用得上、怎么用，按内容判断。

## 讲法

- **从最底层推起，一条问题链。** 全片围绕一个问题展开，每个画面回答上一个画面留下的问题，而不是按名词分章。删掉后链条不断的画面，多半可以删。
- **先有问题，再给名字。** 术语和方法的名字，在它要解决的问题出现之后再给。
- **缩写第一次出现时展开。** 指令名、术语的缩写，在画面和配音里各给一次英文全称，并说明它做什么。（2026-10-08 用户要求）
- **讲清机制。** 让观众看到具体发生了什么、为什么，而不只是结论。
- **台阶之间：问题收尾，改动开场。** 上一版的问题在上一版的画面上演示并收尾，配音写明是哪一版的问题；新一幕从改动开始，不以问题开场，最多用一句话回指刚才的问题。问题与改动用不同视觉标记区分（例如问题用贴在旧版画面上的“瓶颈”标签，改动用版本名标题卡），避免观众把问题当成新版的特性。（2026-10-21 用户要求）
- **新概念先介绍再使用。** 新概念（如共享内存的 bank）第一次用到时，先用画面介绍它是什么，再用它推导。（2026-10-21 用户要求）
- **结果拆开看。** 一个结果由哪几部分组成、每部分怎么变，比直接给出结果更有意思，也更容易信。
- **难点配一个比喻。** 比喻抓住概念的本质；它和真实做法不同的地方就近说一句。
- **简化要说明边界。** 用特例讲机制时，交代它简化了什么、真实情况多了什么，避免观众把特例当成全部。
- **少字、少数。** 一个画面讲一件事；每个论点只留一个代表性的数；科普口径，不放测量限定和方法说明。
- **画面先行，配音不念画面。** 节奏由画面上的动作决定：先按无声把画面和节拍定下来，再按节拍写配音；画面不停下来等一句话念完，哪里话多就删话，不是把画面放慢。（2026-10-08 用户确认）
- **画面和配音分工。** 画面给出“是什么、有多少、怎么变”，配音讲“为什么”和“现在看哪里”，把前后两个画面连起来。画面上已有的字和数字不再念一遍，最多点一下关键的那一个。
- **配音是适合朗读的短句，用词书面、准确。** 一个动作配半句到一句，可以留白，不必每个画面都有话；不写成可以单独成文的讲稿。“短”指句子长度，不指用词：语体与文章相同，运算与对象用数学和领域术语（外积、相加、矩阵乘、标量、求和），不用“拼”“叠”“塞满”“绑在一起”这类口语替代。（2026-10-13 用户要求）
- **静音仍能跟上主线。** 说明就近标在所指的东西旁边；配音逐句烧成底部字幕，与配音同步，分镜预览里也带上。字幕是配音的文字版，不替代画面上的标注。（2026-10-13 用户要求）
- **音效跟着动作。** 只对应画面上的动作，同一类动作用同一个声音，不抢配音。
- **自查是不是在念 PPT。** 只读配音稿：如果它等于把画面上的字从头念一遍，重写。只看画面：如果跟不上主线，改画面，不是加话。

## 文案的语体

配音、页眉、画面标注与字幕都按文章的语体写：书面、正式，句子短但不口语。“短”靠删掉修饰与从句，不靠换成口头说法。（2026-10-20 用户要求）

- **动作用术语。** 数据的移动写“发送、取回、读回、写入、拷贝”，计算与通信的关系写“重叠（overlap）”，资源写“占用、用满、利用率”；不写“发过去、取回来、灌入、塞满、藏进计算、吃不满链路”。
- **不拟人。** 程序与硬件不“报数”“偏爱”“得停下来等”，写成“先统计数量”“被选中的频率更高”“需要等待”。
- **不设问、不用口头连接。** 开场直接给出问题的对象与结论，不用“能不能……？”；“所以”写“因此”，“要么……要么……”写“一是……二是……”，不用“这一次”“就不划算了”“反而”“多半”。
- **主语写全。** 口语常省主语、用“这”“它”指代；字幕单独出现时没有上下文，每句写出主语。

| 口语 | 书面 |
| --- | --- |
| token 要发过去，算完再取回来 | token 发送到 expert 所在的卡，计算后取回 |
| 收多少要先报数，CPU 得停下来等 | 接收方需要先获知数量，CPU 因此等待 |
| 要么少走慢的链路，要么把通信藏到计算后面 | 一是减少经过慢速链路的数据，二是让通信与计算重叠 |
| 单位太小吃不满链路 | 传输单位过小，链路带宽用不满 |
| batch 摊薄了权重，摊不薄 KV cache | batch 均摊了权重的读取，KV cache 无法均摊 |
| 这个速度，能不能在运行之前就算出来？ | 这个速度可以在运行之前估算出来。 |
| 再分出 SM 就不划算了 | 再分出 SM，收益低于代价 |
| 显存满了，回来时要重算 | 显存占满后，恢复时须重算 |
| 送不回时，从共享池拉取 | 否则从共享池拉取 |
| 算完一层、传一层 | 每层计算完成后传输该层 |
| 先拷完才能释放 | 拷贝完成后才能释放 |
| 出了机器，带宽只剩不到三分之一 | 跨机时，每张卡的带宽不到机器内的三分之一 |
| 每张卡都在同时收发，数量由 router 当场决定 | 每张卡同时发送和接收，数量由 router 在运行时决定 |
| CPU 一旦停下等待，这个办法就失效了 | CPU 若需要等待，CUDA graph 无法使用 |
| 一半传，另一半算 | 一半通信，另一半计算 |
| 发出就返回 | 发送后立即返回 |

**流程。** 文案写完、渲染之前，用 `de-ai-edit` skill 把 `script.js` 的页眉与配音、`scenes.js` 的画面标注交给不带写作上下文的 subagent 逐句改一遍。新发现的口语说法补进上表。

## 让人看得懂

- **每样东西先交代来历。** 数据、对象、例子第一次出现时，让观众看到它从哪里来：是整体里的哪一部分，怎么取出来的。交代过一次，后面指回去即可，不必重演。
- **一次只跟一个例子。** 演示一个计算时，只跟一个对象走完全过程，每一步的输入、输出和对应关系都画出来；规则讲清之后，其他例子才快速带过。
- **连线和位置有含义。** 线、箭头、对齐关系对应真实的关系；看不出谁对应谁的图，不如不画。
- **前后对得上。** 同一个对象在全片用同一种画法和颜色；后面用到前面的东西时，画面上认得出来。
- **让观众自己看出来。** 效果能直接看见的，就让它被看见，而不是用数字转述；速度、大小、差距这类量，尽量按真实的比例或速率呈现，让人直接感受到。
- **比较放在同一条基准上。** 要比的东西对着同一条线、同一个尺度，谁多谁少一眼可见。
- **让画面讲道理。** 能用真实数据就用真实数据；示意内容标明。
- **用实机材料作证。** 讲到程序、指令或性能时，放真实的代码、编译结果、程序输出、trace 与实测数字，让观众看到它确实这样运行；只有示意图和引用的数字，画面单调，也像是编的。实测与引用的数字在画面上分得清。实测不是必须的，只在能明显提高表现力时加；草稿期不测，先在画面上留占位，方向确认后再补。（2026-10-08 用户要求）

## 画面

- **封面有一个视觉重点。** 一眼能看到主体，并且这个主体自然过渡到第一个论点，而不是与内容无关的装饰。
- **首尾呼应。** 结尾回到开头的画面，让观众看到这一路改变了什么。
- **画面单独设计，色彩与风格保持一致。** 按主题设计画面构成与节奏，色彩和整体风格沿用系列，不大幅更换。
- **看成片检查。** 在目标观看尺寸下确认文字清楚、无裁切、转场顺畅。

## 表达形式：按内容选，不套模板

色彩、字体、标注样式这类**视觉语言**全系列统一；**表达形式**（平面还是立体、镜头怎么走、动画怎么组织、一屏放什么）每部视频按内容单独选，不沿用上一部的版式。默认做出来的画面容易平、静、每幕一个样，像流水账，以下几条用来避免。（2026-10-21 用户要求）

- **先问"这个内容最适合怎么看"。** 动笔前对每个关键概念想一想它本来的形状：层级与包含关系（grid → block → warp → thread、嵌套的存储层级）适合立体或逐层推镜头；数据流动适合沿真实路径移动的粒子或块；时间上的重叠适合并排的时间线；比例与差距适合按真实比例的长度、面积或赛跑。概念有空间结构时用立体画面讲，不压扁成平面方格。
- **画面要动起来，而且动的是机制本身。** 循环要真的走起来（k 一步步前进、块一块块滑进缓存、结果一层层累加），而不是只给最后一帧加一句说明；镜头推进、放大、拉远表达"进入下一层""回到全局"。静止的图只留给需要停下来读的结论。
- **完整交代对象，不给碎片。** 讲矩阵计算时把参与的矩阵完整画出并标尺寸（例如 A、B、C 按经典位置排开），再高亮正在用的行、列或块；只画一个孤立的小块，观众看不出它从哪来、和谁相乘。缩小的示意要写明缩小了什么。
- **代码、数据、硬件同时同步。** 讲一段代码时，正在执行的那一行、它读写的数据、对应的硬件状态在同一时刻一起变化；代码只放改动的几行，放大到能读，不让它被裁切或遮挡。
- **一条主线，台阶有起伏。** 用一句话主线把各幕串成因果链，而不是"这一版、下一版"地罗列；每个台阶先给证据、再改动、再推出预测、最后用实测对照，对上了是高潮，没对上就照实讲并引出下一步。不同台阶的分量不同：转折点给足时间，小改动可以短，但短不等于一闪而过。
- **结果图不单独占一幕。** 只表达一个结论的图（一条折线、一组柱子、一场赛跑、一个"快了 N 倍"）信息量小，不单独占一整幕或整屏。默认做法是把结果嵌进讲机制的画面：作为角落里随台阶更新的小仪表或小阶梯，或者在机制动画结束时叠一条进度条、一个数字，几秒内收起。只有两种情况可以给结果图整屏：全片或一集的总结，以及结果本身就是要讲的机制（例如按规模变化的曲线揭示了功耗墙）。一幕只有一张结果图时，把它并进前一幕的"实测"那一拍。（2026-10-21 用户要求）
- **细节不藏进快剪。** 压缩时间靠合并相近的步骤、删掉重复的说明，不靠把画面一闪而过；观众需要看清的数字和变化至少停留到读完。
- **关键画面可以先试几种形式。** 一段内容拿不准怎么表现时，先只做这一段的 2–3 种短样片对比，再推广到全片；样片保留原方案中已被认可的部分，只在要解决的问题上做变化。
- **反例自查。** 只看画面、关掉声音：如果每幕版式相同、只是换了标题和数字，或者整片几乎没有运动，就是流水账，回到第一条重新想形式。

## 分镜审阅

- **按幕做关键帧。** 动画之前先交关键帧：一幕一张，画的是这一幕讲完时的画面。
- **每幕配一段可播放的视频。** 只看静态图判断不了节奏和讲解是否跟得上；每幕单独渲染成短片，先交无声的版本定节奏，配音写好后再带上，改哪一幕就只重渲哪一幕，做好一幕先交一幕，不等全片。（2026-10-08 用户要求）
- **每幕下面放对应的文案。** 关键帧与这一幕的配音稿排在一起，标出每句对应哪个动作，一页看完全片的画面和话；方向确认后再做动画，画面节拍定稿后再录配音。（2026-10-08 用户要求）

## 交付前自查

把自己当成没看过文章的观众，逐个画面过一遍；答不上来的地方先自己改，再交给用户：

- 画面上的每样东西是什么，从哪来的？
- 结果是怎么算出来的，哪个输入对应哪个输出？
- 这一幕回答的是什么问题，和上一幕是什么关系？
- 去掉这一幕，后面还讲得通吗？
- 这一幕的形式是为这个内容选的吗？换成别的主题能原样套用的版式，多半没选对。
- 有空间或层级结构的概念，是否用了立体或逐层放大的画法？循环和数据流动是否真的动起来了？
- 有没有整幕或整屏只放一张结果图（折线、柱子、赛跑）的画面？不是总结、也不是在讲机制的，并进相邻的机制画面里。
- 只读字幕，每句是否是书面语、主语是否完整？

## 文件与发布

一个主题只保留一个版本的视频，目录名与文章 slug 相同。（2026-10-07 用户确认）

新视频用 HyperFrames 做，从 `node videos/_kit/tools/new.mjs <slug>` 开始；流程、锁死的风格与“变化轴”见 [videos/_kit/README.md](../videos/_kit/README.md)，每部完成后在 `videos/EPISODES.md` 记一行。HyperFrames 项目的成片在 `videos/<slug>/renders/`，配音在 `videos/<slug>/assets/vo/`，都不进仓库。2026-10 之前的 canvas 视频保持原样，不迁移。（2026-10-26 用户确认）

| 内容 | 位置 | 是否进仓库 |
| --- | --- | --- |
| 源文件（HTML、JS、渲染脚本、文案） | `videos/<slug>/` | 是 |
| 成片 | `videos/<slug>/build/<slug>.mp4` | 否 |
| 配音、分段缓存、草稿、检查截图 | `videos/<slug>/build/` | 否 |
