## 一次申请的配置与依赖

- 单个 Secure 按需 Pod，GPU 数量 8；并发 1，创建次数 1，不自动重建、重试实验或改用其他型号、MIG、多个单卡 Pod。
- 已从官方模板目录核对镜像 `runpod/pytorch:1.0.2-cu1281-torch280-ubuntu2404`，CUDA 12.8.1、Ubuntu 24.04。直接固定镜像，仅映射 SSH 端口，不启动 Jupyter。
- SSH 采用官方镜像启动脚本读取的 `PUBLIC_KEY`，公钥仅用于本轮 Pod；不要混用平台 basic SSH 的 `SSH_PUBLIC_KEY`。真实公钥与本机私钥均不写入仓库；私钥不上传。最终前置检查发现原私钥有口令且 agent 未加载对应钥，因此在仓库外生成本轮专用临时 Ed25519 密钥，仅向本 Pod 注入公钥，不修改账户密钥；释放后删除临时私钥。
- 使用随 Pod 提供的 CPU 与主机内存；取得实际报价和配额后核验至少 8 vCPU / 16 GiB。CPU、内存与 GPU 的计价以整 Pod 返回的报价为准，不将未查询到的附加费用当作零。
- 容器磁盘 40 GB，不申请 volume disk 或 network volume。结果逐阶段保存并回传仓库外的本机目录，清理前检查回传文件完整性。
- 测试工具沿用原计划：NCCL 2.27.7、nvbandwidth commit `1aa9e818d0728c25c87e121d692d829db2239720`、nccl-tests commit `2535da805b34e96d1dc08be66289be1a6d57f5ad`，编译目标 `sm_120`。
- 工具已在无 GPU 的 Linux x86_64 / CUDA devel 环境编译验证；但 314 MiB 归档的 Modal 回传反复失败，停止该传输路径。修订为在 Runpod 内按固定脚本一次安装依赖和编译，整个准备阶段最多 240 秒，费用计入本轮预算；失败即保存记录并退出，不重试安装或另开资源。
- 一次上传套件和 `scripts/runpod-rtx-topology-direct.sh`，一次 SSH 入口执行依赖准备与全部实验。准备仅安装已明确的软件包、NCCL 2.27.7 和固定 commit 的工具，验证 CUDA 12.8 及 `sm_120`；不边占用设备边探索依赖。
- 原有 `scripts/rtx-topology-suite.py` 直接复用；实际设备型号、卡数、P2P 能力及 NUMA 可见性在同一次 GPU 调用内核验。环境不符则保存原因并停止。

## 收尾控制与执行门槛

- 本机 2.14.0 的 `pod create --help` 没有 `--terminate-after` / `--stop-after`；不得照搬技能示例中的未支持参数。
- GPU 申请前必须完成独立于 SSH 的本地监管与收尾控制验证：正常结束、子进程异常、SSH 断连、就绪超时、总期限触及时都查询并停止本轮真实 Pod。创建返回不明确时先按本轮唯一名称查询已有资源，不重新创建。
- `--wait-timeout` 只约束 CLI 等待，不释放资源；测试进程退出也不停止 Pod。停止前回传已有文件；无法回传时在预算期限内终止计算并明确数据损失风险，不无期限保持 GPU。
- 本轮不持久化个人文件或长期环境。结果回传核对完成后删除本轮临时 Pod，再通过列表核查资源已清理；不触碰其他任务的资源。
- 启动门槛：余额足够、现有 SSH 密钥方案确定、固定依赖与测试入口就绪、无 GPU 检查通过、监管控制验证通过、当前费率与预算再次核对。当前仍处于准备阶段，尚未申请 Runpod GPU。
