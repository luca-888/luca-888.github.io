## 全片的问题

一块 H100 跑 Qwen3-8B，生成一个 token 至少要多久？这个数能不能在运行之前估出来？

链条：实测 6.84 ms（开场）→ 一个 token 要搬多少、算多少（2）→ 两种速度、两条时间，取长的那条（3）→ 比值有名字，画成 roofline（4）→ batch 把点往右推（5）→ prefill 落在平顶上（6）→ KV cache 推不动（7）→ KV 能放多少由显存账决定（8）→ 放满之后一步的下限（9）→ 什么手段能移动这个点（10）→ 回到开场（11）。

## 贯穿全片的图形

**一步的时间轴**：一根以毫秒为单位的横轴，上面两条并排的条：搬运（字节 ÷ 带宽，蓝）与计算（运算 ÷ 算力，teal）。一步至少要等较长的那条走完。两条始终按真实比例画：第 3 幕计算条只有搬运条的 1/320，几乎是一条线。实测值是轴上的一个黑色刻度，标“实测”。

第 4 幕起加上 **roofline 图**（对数坐标），同一个场景在两张图上各占一个位置：时间轴回答“多久”，roofline 回答“卡在哪”。之后每一幕都在这两张图上移动同一个点。

颜色沿用系列：权重与搬运 blue，计算 teal，KV cache purple，activation yellow，开销与“差距” red。

## 分镜（11 幕）

每幕一行写“讲完时的画面”，下面是这一幕的文案；配音句后括号里是它对应的画面动作。数字只在画面上出现，配音不念。

### 1 开场 · 约 12 s

**画面问题**：生成一个 token 至少要多久？

**讲完时的画面**：左边一个对话窗口按实测速度（145 tok/s）逐 token 流出回答；右边一块 H100（官方产品渲染图，做减法后用）；下方出现时间轴，第一个刻度落下：实测 6.84 ms。大标题“LLM 推理的量级估算 · Roofline”随后缩到左上角成为页眉。

**画面上的字**：Qwen3-8B · H100 · vLLM；每个 token 6.84 ms（实测）

**文案**
- 一块 H100，运行 Qwen3-8B，只服务一个请求。（窗口开始流出文字）
- 这个速度，能不能在运行之前就算出来？（刻度落在时间轴上）

**音效**：每个 token 一声极轻的 tick，刻度落下一声 land。**出处**：本站 vLLM 实测。

### 2 一个 token 要做什么 · 约 18 s

**画面问题**：生成一个 token，GPU 要做哪些事？

**讲完时的画面**：36 层堆叠；放大其中一层，7 个权重矩阵按真实面积画出（q、k、v、o、gate、up、down，k 与 v 只有 q 的 1/4）；一个 token 的向量依次穿过它们，每块矩阵被扫过时亮一下。右边两个累加计数器：从显存读出的字节 15.1 GB，乘加运算 15.1 GFLOP。最后两数之间出现比值：每字节 1 次运算。

**画面上的字**：每个权重：读 2 字节，做 1 次乘加（2 次运算）；15.1 GB / 15.1 GFLOP

**文案**
- 一个 token 要依次经过全部 36 层。（层堆叠展开）
- 每个权重从显存里读出来，只参与一次乘加，就被丢掉。（向量扫过矩阵）
- 所以搬运的字节数和运算次数几乎相同。（比值出现）

**简化**：attention 读 KV 的部分在第 7 幕单独讲；这里上下文很短，可以忽略。

### 3 两种速度 · 约 18 s

**画面问题**：15.1 GB 和 15.1 GFLOP，哪个更花时间？

**讲完时的画面**：H100 两个规格并排：Tensor Core 989 TFLOPS（BF16），HBM3 3.35 TB/s。时间轴上两条条形：搬运 4.52 ms，计算 0.015 ms（细到要加放大框才看得见）。下限 = 较长的一条 4.52 ms；开场的实测刻度 6.84 ms 在它右边，中间的空隙标红：66%。

**画面上的字**：时间 = 字节 ÷ 带宽；时间 = 运算 ÷ 算力；下限 4.52 ms；实测 6.84 ms

**文案**
- GPU 有两个速度上限：每秒能算多少，每秒能从显存读多少。（两个规格出现）
- 两段时间放在同一根轴上，计算几乎看不见。（两条条形长出，放大框）
- 一步至少要等权重读完。（下限刻度）
- 实测多出的部分，来自 kernel 达不到峰值带宽，以及每一步的调度开销。（红色空隙）

**出处**：NVIDIA H100 规格页（dense）；本站实测。

### 4 算术强度与 roofline · 约 20 s

**画面问题**：差距这么大，用一个数怎么描述？

**讲完时的画面**：上方公式：arithmetic intensity = 运算 ÷ 字节；decode 为 1。H100 的两个规格相除得到 295：每读 1 字节要做 295 次运算，计算单元才不空等。下方 roofline 图从时间轴“立起来”：斜线是带宽，平顶是算力，拐点在 295。decode 的点落在最左端，纵坐标 3.35 TFLOPS，旁边标“峰值的 0.3%”。右上角缩略图：Williams 等 2009 年论文的 Fig. 1（原图），注“原文称 operational intensity”。

**画面上的字**：arithmetic intensity（FLOP / byte）；拐点 295；decode：1

**文案**
- 运算次数除以字节数，称为 arithmetic intensity。（公式出现）
- H100 要每读一个字节做二百九十多次运算，算力才用得满。（295 出现）
- 把两个上限画进一张图，就是 roofline：左边受带宽限制，右边受算力限制。（斜线、平顶依次画出）
- decode 落在最左端。（点落下）

**出处**：Williams、Waterman、Patterson，CACM 2009。

### 5 batch：一次读取，多次使用 · 约 20 s

**画面问题**：怎样把点往右推？

**讲完时的画面**：对话窗口从 1 个变成 8 个，同时流出文字，速度与开场几乎相同。时间轴：搬运条仍是权重的 4.52 ms，计算条变成 8 倍仍然很短；实测刻度从 6.84 移到 7.03 ms。roofline 上点从 1 沿斜线移到 8。旁边一行实测：145 → 1118 tok/s。最后斜线上标出要走到拐点需要的 batch：约 295。

**画面上的字**：8 个请求共用一次权重读取；强度 1 → 8；实测 6.84 → 7.03 ms，145 → 1118 tok/s

**文案**
- 八个请求一起计算，权重只读一次，产出八个 token。（8 个窗口出现）
- 每一步几乎不变慢，吞吐接近八倍。（刻度只挪了一点）
- batch 每增加一倍，点就沿斜线上移一倍，直到拐点。（点沿斜线移动）

**出处**：本站实测（并发 1 与 8）。

### 6 prefill：落在平顶上 · 约 16 s

**画面问题**：有没有一开始就在拐点右边的情形？

**讲完时的画面**：一段 2048 token 的 prompt 一次送进模型，同一份权重被 2048 个 token 共用。时间轴上两条条形的长短对调：计算 28.8 ms，搬运 4.52 ms。roofline 上一个新点（prefill，另一种形状）落在平顶上，强度约 2000。两点各带标签：prefill 受算力限制，decode 受带宽限制。

**占位**：prefill 用时随 prompt 长度的实测曲线（64 → 8192 token），预期在约 300 token 处出现拐点；需要 H100，见 notes 的可选实测。没测之前这一格只放估算的两条条形，不放曲线。

**文案**
- prefill 一次处理整段 prompt，每个权重被两千多个 token 共用。（prompt 送入）
- 这次是计算那条更长。（条形对调）
- 两个阶段落在拐点两侧，原因是同一个比值。（两点标签）

### 7 KV cache：batch 摊不薄的部分 · 约 20 s

**画面问题**：batch 能一直把 decode 推到拐点吗？

**讲完时的画面**：每个请求旁边多出一条自己的 KV cache（紫），长度与上下文成正比：每 token 144 KiB。时间轴的搬运条分成两段：权重（固定）+ KV（随 batch × 上下文增长）。64 个请求、每个 2048 token 时，KV 19.3 GB 已经超过权重 15.1 GB。roofline 上拆出第二个点：attention，强度约 4，batch 再大也不动；矩阵乘法的点继续右移。

**画面上的字**：每 token 144 KiB = 36 层 × 2 × 8 个 KV head × 128 × 2 字节；attention 强度 ≈ 4，与 batch 无关

**文案**
- 权重被所有请求共用，KV cache 只属于自己的请求。（紫色条逐个长出）
- batch 再大，attention 也是每读一个字节只做几次运算。（attention 点停住）
- 上下文一长，每一步搬运的大头就从权重变成了 KV cache。（搬运条里紫色超过蓝色）

**简化**：attention 强度约 4 来自 GQA（32 个 query head 共用 8 个 KV head）；MLA 不同，第 10 幕交代。

### 8 显存账 · 约 20 s

**画面问题**：KV cache 最多能放多少？

**讲完时的画面**：一根 80 GB 的显存条，按 vLLM 启动日志逐段填入：权重与非 torch 16.17 GiB，activation 峰值 1.68 GiB，CUDA graph 0.45 GiB，KV cache 54.99 GiB，末端 8% 不用（利用率 0.92）。显存条旁边是真实日志的三行，每段亮起时对应的那一行高亮。KV 段换算成 400,448 个 token，再除以每个请求 2048 → 最多 195 个请求同时运行。

**画面上的字**（日志原文）：`Model loading took 15.27 GiB memory` / `Actual usage is 16.17 GiB for consumed memory (weights + non-torch), 1.68 GiB for peak activation, and 0.45 GiB for CUDAGraph memory` / `GPU KV cache size: 400,448 tokens, Maximum concurrency for 2,048 tokens per request: 195.53x`

**文案**
- vLLM 启动时先加载权重，再按最大的一步空跑一次，量出 activation 的峰值。（权重段、activation 段依次填入）
- 剩下的显存全部分给 KV cache。（紫色段填满）
- 能同时服务多少请求，由这一段决定。（195 出现）

**出处**：本站实测日志；vLLM `gpu_worker.py` `determine_available_memory`。

### 9 一步的下限 · 约 18 s

**画面问题**：显存放满时，一步至少要多久？

**讲完时的画面**：公式落定：一步 ≥ max（字节 ÷ 带宽，运算 ÷ 算力）。代入 195 个请求 × 2048 token：搬运 = 权重 15.1 GB + KV 58.9 GB = 74.0 GB → 22.1 ms；计算 3.0 ms。时间轴上紫色占了搬运条的四分之三。旁边：吞吐上限约 8800 tok/s，是 batch 1 下限（204 tok/s）的 42 倍；每个请求生成一个 token 的下限从 4.52 ms 变成 22.1 ms。

**占位**：decode 每步用时随 batch 的实测点（上下文 2048，batch 1 → 256），叠在这条估算线上；需要 H100，见 notes 的可选实测。

**文案**
- 估算只需要两个数：每步搬运的字节，每步的运算次数。（公式出现）
- 显存放满以后，计算仍然只占一小段，带宽决定了下限。（条形长出）
- 吞吐上去了，每个请求却变慢了。（两个数并排）

### 10 移动这个点 · 约 20 s

**画面问题**：哪些手段能改变这个下限？

**讲完时的画面**：roofline 上三组箭头，各标一个手段：
- FP8 权重：字节减半，点右移、平顶上移到 1979 TFLOPS；
- MLA：每 token KV 从 Qwen-2.5-72B 的 327 KB 降到 DeepSeek-V3 的 70 KB，attention 点右移；128 个 query head 共用一份 latent，decode attention 越过拐点；
- speculative decoding：一次读取验证多个 token，强度乘以候选数。
最后叠上 B200 的屋顶：平顶与斜线都抬高，拐点 281，与 H100 的 295 几乎在同一处。

**画面上的字**：三个手段名与箭头；B200：2250 TFLOPS、8 TB/s、拐点 281

**文案**
- 让每个字节多做几次运算，或者少读几个字节。（三组箭头依次出现）
- 新一代 GPU 的算力和带宽一起增长，拐点几乎原地不动。（B200 屋顶叠上）

**出处**：NVIDIA 规格页；DeepSeek ISCA'25；FlashMLA deep dive。

### 11 结尾 · 约 10 s

**画面问题**：回到开头的问题。

**讲完时的画面**：回到开场的对话窗口与时间轴，这次刻度旁写出它的来历：15.1 GB ÷ 3.35 TB/s = 4.52 ms 下限，实测 6.84 ms。下方三行估算步骤：数字节、数运算、各除以带宽与算力，取较大者。

**文案**
- 运行之前，先数清楚要读多少字节、要做多少运算。（三行步骤出现）
- 哪一项更慢，就卡在哪里。（时间轴回到开场画面）

## 简化之处

- 运算按“每个参数 2 次运算”估；attention 的运算在短上下文下忽略。
- 峰值用规格表的 dense 数字；实际 kernel 很少超过峰值的 80–85%。
- 只讲单卡；多卡时通信可能成为新的下限，片中不展开。
- MoE 只在 notes 里交代：激活参数少，但每个 expert 分到的 token 也少，强度不一定上升。

- 配音约 330 个汉字，讲“为什么”和“看哪里”，不念画面上的数字。
