# matmul-ladder-tc-hf 配音稿

每幕一个 `## 幕 id`，每行一句配音（即一条字幕）；`# 动作：` 行是这句对应的画面动作，配音脚本跳过。第六版（2026-10-27）按 OUTLINE.md：教原理，全片挂在一张存储层级图上；证据见 CONCEPT.md。

## s01
H100 芯片上，132 个 SM 分为上下两半，中间是 L2 缓存，显存位于芯片两侧。
# 动作：芯片全景淡入；SM 网格、中间的 L2、两侧显存依次亮起。
每个 SM 里有 4 个 Tensor Core，专用于矩阵乘法：一条指令完成两个小矩阵的乘法，速度为普通计算单元的 16 倍。
# 动作：镜头推进到一个 SM，再落到 Tensor Core；两块小矩阵飞入，一块结果飞出；旁边普通单元一次只算一个乘加。
但 Tensor Core 只能计算已经送达的数据。
# 动作：Tensor Core 前面的输入槽变空，闪烁等待。
数据从显存出发，先进入 L2，再进入每个 SM 的 shared memory，即片上共享内存，然后读入寄存器，最后交给 Tensor Core。
# 动作：存储层级图从下往上搭起：显存、L2、shared memory、寄存器、Tensor Core，说到哪层亮哪层，层间箭头依次画出。
计算结果再从寄存器写回显存。
# 动作：右侧画出一根从寄存器回到显存的写回箭头。
在最简单的实现中，数据逐层送达太慢，Tensor Core 每算一次都要等待。
# 动作：一块数据沿图缓慢上行，Tensor Core 亮一下就灭，空转；右上角速度条出现，停在很短的一截。
右上角的速度条以英伟达官方矩阵库 cuBLAS 为满格。
# 动作：速度条右端的满格刻度高亮，标注 cuBLAS。
优化共有七步，每一步消除一处等待：前四步在 SM 内部，后三步在 SM 之外。
# 动作：七个优化标题依次挂到图上各自作用的那一层旁边；SM 内部、SM 之外两个区域分别框出。

## s02
第一处等待位于从 shared memory 读入寄存器的环节。
# 动作：图上这一段点亮，其余变淡；标题“swizzle：把数据错开存，避免 bank 冲突”出现；随后图缩到左上角，主画面换成 32 根 bank 柱。
shared memory 分成 32 个 bank，即存储体；同一周期内，每个 bank 只能送出一份数据。
# 动作：32 根 bank 柱排成一排，每根顶上一个出口，一拍各吐出一格。
一个 warp 的 32 个线程同时读取：地址落在不同 bank 时，一个周期即可读完；落在同一个 bank 时，只能排队，每轮读取一份。
# 动作：32 根箭头分散射入 32 根柱，一拍全亮；再换成几根箭头挤进同一根柱，逐个出队。
这种情况称为 bank conflict，即存储体冲突。
# 动作：挤在一起的那根柱标红，打出“bank conflict”。
矩阵在 shared memory 中按行存放，而 Tensor Core 所需的数据须纵向跨越多行读取。
# 动作：矩阵一行行铺进 bank 柱上方；一条竖条框住 8 行的同一位置。
若一行恰好覆盖所有 bank 一圈，各行的同一位置会落在同一个 bank 上，8 行须分 8 轮读完。
# 动作：8 行同一位置的格子全落进同一根柱，排成一摞，逐个送出，计数跳到“8 轮”。
解决方法称为 swizzle，原意为搅乱：写入时，每一行的数据块按行号重新排列。
# 动作：8 行的数据块各自滑动换位，原来竖成一列的 8 格变成一条对角线。
纵向读取时，8 行落在 8 个不同的 bank 上，一个周期即可读完；数据量不变，只是位置改变。
# 动作：对角线 8 格同时落进 8 根不同的柱，一拍齐出，计数“8 轮 → 1 轮”。
读取方也须知道新位置，因此改用 PTX 的 ldmatrix 指令，由每个线程计算换位后的地址。
# 动作：一行大号代码 ldmatrix(… swz(r, c))，8 根细线从代码连到对角线上的 8 格；速度条前进。

## s03
第二处等待位于搬运环节，即数据从 L2 送入 shared memory。
# 动作：小地图上 L2 → shared memory 一段点亮；标题“cp.async：搬运不经过寄存器”出现。
在最简单的实现中，线程先把数据读入自己的寄存器，再写入 shared memory；数据传输期间，线程只能等待。
# 动作：一块数据从 L2 出发，绕进寄存器再拐进 shared memory；下方时间线上“搬”一格画完，“算”才开始，Tensor Core 那一行留出空白。
cp.async 是一条异步拷贝指令：数据从 L2 直接写入 shared memory，不经过寄存器；指令发出后，线程无须等待数据到达。
# 动作：绕路的箭头被拉直成一根直达箭头；线程图标发出指令后立即转身去算。
仅仅不等待还不够，下一块数据须提前开始传输。
# 动作：时间线上出现“下一块”的方块，从更早的位置开始移动。
因此在 shared memory 中设置几块缓冲轮流使用：计算当前一块时，后续几块已在传输中。这种安排称为流水线（pipeline）。
# 动作：shared memory 里画出 3 格环形缓冲，“搬”和“算”沿环转动，各占一格。
搬运与计算由此重叠，Tensor Core 等待数据的时间大幅减少。
# 动作：时间线从“搬、算、搬、算”的串行收拢成上下两行重叠，Tensor Core 那一行的空白变短；速度条前进。

## s04
第三处等待来自指令本身。
# 动作：小地图上 shared memory → Tensor Core 一段点亮；标题“wgmma：换一条更大的指令”出现。
此前使用的 mma.sync 每条只计算一小块，操作数还须先从 shared memory 读入寄存器。
# 动作：Tensor Core 前面排着一长串小方块指令，每块都要先经过寄存器。
实测中只连续发出 mma.sync、不读取任何数据，吞吐也只有 Hopper 新指令的三分之二。
# 动作：两根并排的柱：mma.sync 只长到新指令的三分之二处停住。
Hopper 的新指令称为 wgmma：4 个 warp 组成一个 warpgroup，共同发出一条指令，计算一大块；操作数直接从 shared memory 读取，无须先进入寄存器。
# 动作：一串小方块合并成一整块大方块；图上“shared memory → 寄存器”这一段淡出，箭头从 shared memory 直接指向 Tensor Core。
与之配套的还有两项新硬件。TMA 即张量内存加速器，一条指令即可把一整块数据搬入 shared memory，并在搬运时完成 swizzle。
# 动作：TMA 把一整块推进 shared memory，落下时自动排成对角线。
mbarrier 是 shared memory 中的计数器，数据到齐后，mbarrier 通知计算方开始计算。
# 动作：计数格一格格填满，满了亮灯，Tensor Core 开始算。
此后搬运由 TMA 完成，读取由 wgmma 完成，线程只负责发出指令。
# 动作：三者各占图上一段同时亮起；速度条前进。

## s05
第四处等待来自分工。到这一版为止，同一批线程仍既发出搬运指令，又发出计算指令。
# 动作：标题“warp specialization：一组专门搬，一组专门算”出现；一排线程图标同时挂着“搬”和“算”两个标签。
每算完一块，所有线程须同步，确认这一块已经用完，才能开始下一块；同步期间 Tensor Core 处于空闲。
# 动作：时间线上每块计算之后出现一道竖线（同步），竖线前后 Tensor Core 那一行留空。
解决方法是分工，即 warp specialization：一组 warp 只负责发出 TMA 搬运，称为 producer；另外两组只负责计算，称为 consumer。
# 动作：线程图标分成上下两组，上面一组标“搬”，下面两组标“算”。
双方通过 mbarrier 交接：数据到达后，consumer 开始计算；缓冲用完后，producer 立即补充。
# 动作：两条泳道之间的计数格亮灭交替，数据块从上道递到下道，空格从下道还给上道。
搬运始终提前几块，两组 consumer 轮流使用 Tensor Core，块与块之间不再有空闲。
# 动作：Tensor Core 那一行的空白一格格被填满，连成一整条；速度条前进。

## s06
SM 内部的等待消除之后，矩阵增大时速度不再提升，此时的等待来自显存。
# 动作：小地图上显存 → L2 一段点亮、变红；标题“tile 分组：让共用的数据趁热复用”出现。
大矩阵被切分为许多小块，称为 tile，每个 SM 计算一块；一百多个 tile 同时计算，同一列的 tile 都需要同一块 W。
# 动作：结果矩阵 C 画成网格；左边 A、上面 W；选中一列 tile，W 上对应的一块同时高亮。
按行依次发放时，共用同一块 W 的 tile 开始时间相隔很久。
# 动作：网格按行一格格亮起；同一列的两格之间隔了很多拍。
后一个 tile 使用时，这块 W 已被其他数据挤出 L2，只能再从显存读取一次。
# 动作：W 块进入 L2，又被后来的数据挤出去；同一块 W 第二次从显存读入，显存箭头反复闪。
改为分组发放：每 16 行组成一组，组内按列发放，共用 W 的 16 个 tile 几乎同时开始。
# 动作：网格换成分组顺序，一列 16 格同时亮起。
一块 W 读入 L2 后，随即被这 16 个 tile 共同使用；仅改变发放顺序，显存读取量就大幅减少。
# 动作：一块 W 进入 L2，分出 16 根线连到 16 格；显存 → L2 的箭头变细；速度条前进。

## s07
显存读取减少后，L2 成为最繁忙的环节：相邻两个 SM 需要同一块数据时，各自从 L2 读取一次。
# 动作：小地图上 L2 → shared memory 一段点亮；标题“cluster 多播：读一次，两个 SM 共用”出现；L2 向两个 SM 各射出一根箭头，载着同样的数据。
Hopper 新增了 thread block cluster，即线程块集群：若干线程块组成一组，位于相邻的 SM 上，可以互相访问 shared memory。
# 动作：两个 SM 被一个框圈在一起，框上标“cluster”。
组内使用 TMA 多播（multicast）：共用的数据只从 L2 读取一次，同时写入两个 SM 的 shared memory。
# 动作：两根箭头合成一根，到 cluster 门口再分叉，同时落进两个 SM；L2 的忙碌度下降；速度条前进。

## s08
最后一处等待来自写回：每算完一块，结果须从寄存器写回显存。
# 动作：小地图上寄存器 → 显存的写回箭头点亮；标题“TMA store：写回时不停算”出现。
原先每个线程分散写出自己的那份结果，写完才能开始下一块；写回期间 Tensor Core 处于空闲。
# 动作：寄存器向显存射出一大把细箭头；时间线上每块计算之后跟着一段写回，Tensor Core 那一行留空。
改用 TMA 写回：计算方先把结果写入 shared memory，由一个线程发出一条指令，TMA 把整块写回显存。
# 动作：细箭头收拢成一根粗箭头，先进 shared memory，再由 TMA 推回显存。
计算方随即开始计算下一块，写回与计算由此重叠。
# 动作：时间线上写回段移到下一块计算的下方，Tensor Core 那一行连成一整条；速度条前进。

## s09
在这张图上，前四步位于 SM 内部：读取不再冲突，搬运不占用线程，指令更大，搬运与计算分工。
# 动作：小地图放大回整屏；SM 内部的四个标题依次点亮各自那一层。
后三步位于 SM 之外：减少显存与 L2 的读取，并使写回与计算重叠。
# 动作：SM 之外的三个标题依次点亮。
经过七步优化，手写版本的速度与 cuBLAS 基本持平。
# 动作：速度条走到与 cuBLAS 满格齐平。
矩阵乘法的速度取决于两点：Tensor Core 等待数据的时间，以及计算所用的指令。
# 动作：一块块数据流畅地沿图上行，Tensor Core 持续亮着。
