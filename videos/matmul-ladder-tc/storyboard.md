## 一页视觉设计说明

### 主线

**Tensor Core 的峰值固定，每一步改动都是让数据更早、更快地送到它面前。** 全片用同一座“硬件塔”（显存 → L2 → 共享内存 → 寄存器 → Tensor Core 五层立体板）作主轴：每一步只改数据在塔上走的路径，路径上流动的小方块（A 蓝、W 黄、结果紫）就是代码改动的硬件侧效果。瓶颈在哪一层，那一层或那一跳标橙并贴“瓶颈”标签；下一幕以“第 N 步：改动”开场，第一句回指这个标签。

一句话因果链：FP32 单元用满 → 换 Tensor Core（wmma，93）→ 数据两次经过寄存器、bank 冲突 → 换位 + cp.async 直达共享内存（269，3 倍跳）→ 每块等拷贝 → 三级缓冲（309）→ 每个 warp 仍经寄存器发小指令，停在约 300 → TMA + wgmma 直接从共享内存读（484）→ 同一 warpgroup 既拷贝又计算 → warp 特化（480，8192 阶不涨）→ 原因：W 128 MB 超出 L2 → tile 分组发放（740，大跳）→ 每个 block 各自从 L2 读 W → 集群多播（757）→ 零散写回 → TMA 写回（777.6，cuBLAS 的 99.5%）→ 持续运行受 700 W 功耗墙，两者都用到 1360 MHz 峰值的 93%。

### aha 点

1. **一条指令一个块**（第 1 幕）：FP32 一次乘加是一个点；Tensor Core 一条指令是一整个乘加立方体同时点亮；2048 个点与 128 个点按同一点距画，面积即 16 倍。
2. **数据两次经过寄存器**（第 2 幕）：塔上路径向上、折回、再向上，观众直接看到绕路。
3. **8 轮 → 1 轮**（第 3 幕）：8 行同一块叠在同一组 bank，异或换位后变成对角线，底部的请求计数从一列 8 变成每列 1。
4. **wgmma 的指令体积**（第 5 幕）：64 × 128 × 16 与 16 × 8 × 16 按体积并排，差 64 倍。
5. **warp 特化为什么不涨**（第 6 幕）：同一改动在 4096 阶 +1/3、8192 阶 0；L2 容量条上 32 MB 放得下、128 MB 溢出；tile 图上一轮 132 个 tile 横跨全部 32 列。
6. **只改发放顺序**（第 7 幕）：同一张 tile 图，一轮从“4 行 × 32 列”收拢成“16 行 × 8 列”，A、Wᵀ 被点亮的部分随之变化，工作集 136 → 65 MB，速度 480 → 740。
7. **首尾呼应**（第 10 幕）：开场的 2048 个点回来，持续运行时点亮 93%。

### 每个新概念的表现形式与理由

| 概念 | 形式 | 理由 |
| --- | --- | --- |
| Tensor Core | 标量乘加（一个点）对矩阵块乘加（等轴测立方体整体点亮）；每 SM 每周期 128 对 2048 个点 | “一条指令算一个小矩阵块”是体积关系，立方体比文字直接；点阵面积按真实比例 |
| 存储层级 | 五层立体板组成的硬件塔，SM 内三层用虚线框住 | 层级与包含关系适合立体、逐层；全片同一画法，后面每一步只改路径 |
| 数据流动 | 沿真实路径移动的小方块；越过的层用白色缺口表示“从它前面经过” | 寄存器折返、直达共享内存、绕过寄存器等差别只能靠路径看出 |
| A / Wᵀ / C | 经典位置排开的完整矩阵，按真实比例标出 block 的块，再用放大镜放大到 warp 与片段 | 用户要求完整对象；按比例的小块交代“从哪来”，放大镜交代“里面是什么” |
| bank 冲突与换位 | 8 × 8 的 16 字节块网格，块按逻辑序号着色，换位时块横向滑到 c ⊕ r；底部是每组 bank 的请求计数 | 换位是空间置换，滑动动画让观众看到对角线如何形成 |
| 多级缓冲 | 矩阵上沿 K 的三个块（计算中 / 已到 / 在途）与共享内存槽位环同色同步轮转；下方两轨时间线 | 时间上的重叠适合并排时间线；三色把“哪一块在哪个槽位”与矩阵对上 |
| TMA | 一整块（已换位的条纹）从 L2 板落到共享内存板，只有一个线程发出 | 与上一版的小方块流对比，“一条指令一整块” |
| mbarrier | 字节计数条从 0 涨到 32 KB，满后 warpgroup 的点由灰变绿 | 它本质是计数器 |
| warpgroup / wgmma | 4 行 × 32 个线程点；指令体积按比例的两个长方体；塔上共享内存 → Tensor Core 越过寄存器 | 同时交代“谁发出”“算多少”“从哪读” |
| warp 特化 | 3 个 warpgroup 方框 + 4 个槽位（带 full / empty 两灯循环）+ 寄存器重新分配柱 + 两个消费者交替的时间线 | 生产者与消费者的分工、两组 barrier 的握手是并行过程，用会转的槽位与时间线表达 |
| tile 发放顺序 | 8192 阶的 C 按 128 × 256 切成 64 × 32 的真实 tile 图，一轮 132 个 tile 用紫色；A、Wᵀ 沿 K 压缩成边条，被用到的部分点亮；工作集条带 L2 50 MB 刻线 | 内容本身是二维的覆盖范围，按真实 tile 数画才能看出 136 → 65 MB |
| 线程块集群 / 多播 | 两个 SM 框进集群，L2 中 W 块的前后两半各由一个 block 发出、分叉写入两边 | 多播是“一次读、两处写”的分叉，箭头分叉最直接 |
| TMA 写回 | 塔上紫色路径反向（寄存器 → 共享内存 → L2 → 显存），旧的直接写显存划掉；时间线上写回段移到 TMA 轨 | 与前面的读取路径对称，观众一眼看出方向反了 |
| 功耗墙 | 同一刻度的四根条（989 / 735 / 682.3 / 681.1） | 比较放在同一基线上 |

### 贯穿全片的统一规则

- **进度只在角落**：右上角的线性小条（8192 阶 TFLOPS，cuBLAS 781.9 虚线），实测那一拍增长并浮出倍数，不单独占一幕；只有结尾总结用一组 8 级的小阶梯。
- **代码不遮挡**：每幕只放改动的 2–6 行（精简自 `matmul_tc.cu`），右侧固定位置，正在讲的行蓝底高亮，`+` 标改动行；与塔上的路径、矩阵上的块在同一拍变化。
- **问题收尾、改动开场**：每幕最后一拍在本版画面上贴橙色“瓶颈”标签；下一幕标题卡为版本名 + “第 N 步：改动”，配音第一句“为了……，第 N 步……”。
- **示意与实测分开**：实测数字来自 `ladder-final-20261021-121144.txt`；推算值（4 路 bank 冲突、136 / 65 MB、8.7 / 5.9 TB/s）在画面上标“推算”；缩小或放大的地方标“按比例”“宽度放大示意”“沿 K 方向压缩显示”。

### 与用户给定口径的核对

- **674 不是等效上限。** 文章写的是：持续满载时 SM 时钟约 1360 MHz，按这一时钟 Tensor Core 峰值 132 × 4096 × 1.36 GHz ≈ **735** TFLOPS；674.88 是 cuBLAS 在 4096 阶连续运行的实测速度。片中用 735，并给出 8192 阶连续运行 682.34（手写）/ 681.14（cuBLAS）≈ 735 的 93%。
- **8.7 → 5.9 TB/s 属于集群那一步**，不是 tile 分组：文章按 `wgmma_pipe` 的耗时推算每个 block 各自从 L2 读 W 时 L2 → SM 约 8.7 TB/s，集群多播后约 5.9 TB/s。tile 分组一步只用工作集 136 → 65 MB；8.7 TB/s 作为它的“问题”出现在第 7 幕结尾。
- **分组后 65 MB 仍大于 L2 的 50 MB**，片中不说“放得下”，只说“减为一半、每块 W 同时被 16 个 tile 读取”。
- `wgmma_pipe`（740.5，无变化）不出现；`wgmma_persist`（657，单独变慢 11%）不单独成幕，在集群一幕作为前提用一拍交代，757 标为“常驻 + 集群 + 多播”。
- 文章开头写“1350 MHz、约 674 TFLOPS”“FP32 止于 44.3”，正文与片中用 1360 MHz / 735、上集结尾 tuned 44.5；文章开头的口径建议另行统一（本次未改文章）。
- 上集结尾的 FP32 成绩用 tuned 的 44.5（cuBLAS FP32 51.7 的 86%）。
